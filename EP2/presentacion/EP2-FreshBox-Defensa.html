CONTEXTO DEL CLIENTE

Caso y necesidad de negocio

FreshBox SpA

  • Negocio: catálogo online de productos orgánicos con despacho en RM.
  • EP1: ALB · EC2 + Docker · MySQL en EC2 · CRUD validado.
  • Límite: SPOF de datos · contenedores acoplados al host · escalado solo de VMs.

Decisión EP2

  • Orquestación: Amazon EKS + Node Group Multi-AZ.
  • PaaS de datos: Amazon RDS MySQL Multi-AZ.
  • Alcance: mismo dominio CRUD; carrito y órdenes fuera de alcance.
EVOLUCIÓN ARQUITECTÓNICA · IE3.1.1

De EP1 (AS-IS) a EP2 (TO-BE)

AS-IS · EP1

EC2 + Docker + MySQL en EC2

  • Cómputo: ASG con 5 contenedores en el host.
  • Datos: MySQL en EC2 (punto único de falla).
  • Ingreso: ALB → Target Group EC2.
  • Límite: escalado de VMs, no por API.
TO-BE · EP2

EKS + RDS MySQL Multi-AZ

  • Cómputo: EKS · Node Group t4g.small (2–4).
  • Datos: RDS Multi-AZ + cifrado.
  • Ingreso: ALB Ingress → pods.
  • Ops: HPA + Container Insights.
LÍNEA BASE

Arquitectura AS-IS (EP1)

Flujo: Internet → ALB → EC2/Docker → MySQL en EC2 · tres capas Multi-AZ

DISEÑO TO-BE · IE3.2.1

Arquitectura EP2 — EKS + RDS Multi-AZ

Flujo: Internet → ALB Ingress → pods EKS → RDS MySQL Multi-AZ · us-east-1 · namespace freshbox

ESTRATEGIA · IE3.1.2

Modelo cloud seleccionado

Técnica

Orquestación + PaaS sobre la misma topología de tres capas.

  • Amazon EKS + Node Group ARM64
  • RDS MySQL Multi-AZ
  • ALB Ingress + Amazon ECR
  • HPA + Container Insights
  • Terraform (IaC del laboratorio)

Financiera

Sizing acotado a AWS Academy Learner Lab.

  • Nodos t4g.small (2–4)
  • RDS db.t4g.small
  • NAT único en laboratorio
  • Mayor densidad de pods por nodo
  • Destroy al finalizar el lab

Estratégica

Continúa el catálogo y prepara la siguiente ola de features.

  • CRUD de productos operativo
  • HA de datos nativa (Multi-AZ)
  • APIs desplegables por separado
  • Base para carrito y órdenes
  • Narrativa clara para el negocio
ARQUITECTURA Y COMPONENTES · IE3.2.1

Servicios AWS del TO-BE

Red e ingreso

VPC Multi-AZ, IGW, NAT y ALB Ingress internet-facing hacia los pods.

Cómputo EKS

Cluster Active con Node Group t4g.small (2–4) y cinco Deployments en namespace freshbox.

Imágenes y datos

Cinco repos ECR ARM64 y RDS MySQL Multi-AZ db.t4g.small con cifrado.

Elasticidad y monitoreo

HPA en backends (~70% CPU) y CloudWatch Container Insights del clúster.

RESILIENCIA · IE3.2.2

Escalabilidad, seguridad y alta disponibilidad

Escalabilidad

Elasticidad a nivel de pod y de nodo.

  • HPA en backends (min/max acotado)
  • Objetivo de CPU ~70%
  • Node Group de 2 a 4 nodos
  • Frontend con réplica fija (lab)

Seguridad

Segmentación y cifrado por capa.

  • SG: Internet → ALB → EKS → RDS
  • TCP 3306 solo desde SG de EKS
  • RDS sin IP pública
  • Cifrado EBS y almacenamiento RDS

Alta disponibilidad

Redundancia entre Availability Zones.

  • Nodos en us-east-1a y 1b
  • RDS Multi-AZ (primary + standby)
  • ALB Multi-AZ
  • Riesgo lab: NAT único (egress)
IMPLEMENTACIÓN · IE3.3.1 / IE3.3.2

Contenedores, CRUD e Insights

Cargas de trabajo

  • 5 Deployments: frontend + get / create / update / delete-product
  • Services ClusterIP + Ingress ALB
  • Imágenes publicadas en Amazon ECR (ARM64)

Validación y operación

  • CRUD: GET · POST · PUT · DELETE vía ALB
  • Datos: persistencia en RDS Multi-AZ
  • Ops: Container Insights + 4 HPA backends
CIERRE

Conclusiones

RESULTADO EP2

Arquitectura modernizada

  • Tres capas conservadas; cómputo en EKS y datos en RDS Multi-AZ.
  • Catálogo CRUD validado vía ALB Ingress.
  • Seguridad por capas, HA Multi-AZ y elasticidad con HPA.
SIGUIENTE PASO

Endurecimiento productivo

  • TLS con ACM · WAF según exposición.
  • NAT por AZ o VPC endpoints hacia ECR.
  • CI/CD completo y pruebas de restauración RDS.
